# 待处理中心工作流设计

日期：2026-09-02

状态：设计稿，待用户审核

## 目标

待处理中心用于集中展示 Server 扫描、AIMES 获取和订单校验产生的、仍需要用户介入的项目。列表负责说明“有什么问题”，右侧详情负责说明“为什么需要处理、会影响什么、下一步是什么”。

本设计只定义待处理分类、右侧详情模板和动作边界，不修改正式 App，不改变 Python 业务规则或 SQLite 事实。

## 已确认的现有事实

- Server 扫描发现变化后，当前项目代码将其归类为 `待扫描处理`；在用户界面中应改称“待处理”，因为用户进入待处理中心时扫描已经完成。
- 当前代码还会生成“需人工确认”“需人工处理”和“处理失败”。
- `factory_ownership`、`server_missing_report`、AIMES review 和 AIMES 格式警告会进入“需人工确认”路径。
- 未映射材料等问题会进入“需人工处理”路径，因为系统必须先打开映射工作台或补充资料，不能直接确认写入。
- “稍后处理”不是状态。它只关闭当前待处理界面，项目仍然保留，下次扫描仍可再次提醒。
- 真实写入必须经过只读预览和显式确认；预览不会写入正式业务事实。

## 待处理类型

### 1. 待处理

含义：扫描已经发现 Server 文件夹或订单文件变化，但尚未进入本次预览处理。

右侧显示：

- 文件夹、订单号和来源文件。
- 发现了哪些变化及其影响范围。
- 当前是否可以进入预览。

操作路径：

1. 在左侧选择要处理的项目。
2. 点击“选择并预览”进入只读预览。
3. 预览结束后，另行点击“确认后写入”并通过二次确认。

“选择”和“预览”可以在界面上表现为一条连续的主要操作路径，但不能把预览和真实写入合并为一个不可区分的动作。

### 2. 处理失败

含义：系统已经尝试读取、解析或处理，但本次失败。

右侧显示：

- 失败发生在哪个阶段。
- 原始错误的用户可理解说明。
- 文件夹或文件路径。
- 对订单数据可信度和后续流程的影响。

操作：

- 检查并确认重试。
- 打开所在位置。
- 稍后处理。

不显示“确认后写入”，因为当前没有可靠的可写入预览。

### 3. 待人工确认

含义：系统已经取得候选结果或发现需要用户作出业务判断，但还不能自动选择。

当前业务会在以下情况进入此类：

- 一个工厂单无法可靠判断属于哪个订单：`factory_ownership`。
- Server 报表缺失，需要人工核对：`server_missing_report`。
- AIMES 工厂单需要用户确认，包括普通 review 和格式警告。

右侧显示：

- 当前来源与可信度。
- 候选项或当前值/建议值对比。
- 选择后会发生的业务变化。
- “只读预览”和“确认后写入”的边界。

操作：

- 打开只读预览。
- 确认后写入。
- 稍后处理。

### 4. 需人工处理

含义：系统已经知道阻塞原因，但还没有可靠的候选结果，必须先由用户补充或修复资料。

典型情况是未映射材料或五金 SKU。

右侧显示：

- 原始名称、规格和来源。
- 缺少或冲突的字段。
- 候选商品及规范化 SKU。
- 映射后会影响哪些订单或工厂单。

操作：

- 打开映射工作台。
- 保存映射。
- 忽略当前项目（仅在现有业务规则允许时）。
- 稍后处理。

## 全局动作

“稍后处理”在四种类型中都可用，但不改变项目的业务状态、不写入基线、不代表问题已解决。第一版继续使用当前语义：关闭当前界面并保留待处理项目。

未来如果需要定时提醒，应新增独立的提醒时间字段，例如 `reminder_at`，不能把“稍后处理”增加为第五种状态。

## 人工映射完成后的自动续跑

“需人工处理”不是流程终点。用户完成材料或五金映射后，系统应继续执行触发该阻塞的原始操作中尚未完成的部分。

推荐流程：

1. 用户从待处理详情点击“处理映射”，进入映射入口。
2. 映射工作台显示原始名称、规格、来源、候选商品和规范化 SKU。
3. 用户保存映射；保存映射本身按现有规则经过明确操作和日志记录。
4. 系统恢复原待处理项目的续跑上下文，包括订单/工厂单、来源文件夹和被阻塞的操作类型。
5. 系统重新读取必要的订单或 Server 文件，并只执行原流程中尚未完成的扫描、解析和校验步骤；不重新执行无关的全量扫描。
6. 重新读取成功后，系统自动打开或呈现对应的只读预览，让用户核对新的结果。
7. 只有用户在预览中另行点击“确认后写入”并通过二次确认，才执行真实业务写入。

如果续跑失败，项目应继续保留在待处理中心，并将新的失败阶段和下一步显示出来；不能因为映射保存成功就把原问题标记为已解决。

### 续跑状态边界

- 映射完成：只表示阻塞资料已补充，不等于订单或 Server 事实已写入。
- 重新扫描/解析：只读或生成预览数据，不等于确认写入。
- 只读预览：向用户展示将要发生的变化。
- 确认后写入：唯一允许推进正式业务事实的动作。

当前代码在保存库存映射后已经会触发重新预检和重新读取订单文件；后续实现应将这两个动作纳入明确的串行续跑上下文，并在结果准备好后回到对应预览，而不是让用户重新寻找原项目。

## 右侧详情的共同结构

每种类型共享以下外壳：

1. 订单或文件夹身份。
2. 来源和更新时间。
3. 当前待处理类型。
4. 影响范围。
5. 类型专属详情。
6. 类型专属操作区。

共享外壳保证学习成本稳定；类型专属区域保证按钮和说明不会与当前问题不匹配。

## 设计验证标准

- 用户能区分“待处理”“处理失败”“待人工确认”和“需人工处理”。
- 用户能理解“稍后处理”只是暂时离开，不是解决问题。
- “选择并预览”不会暗示已经写入。
- 只有“确认后写入”及二次确认才可能触发真实写入。
- 每种类型的右侧都不出现不适用的主要按钮。
- 所有来源、候选值和规范化 SKU 都能追溯到原始业务事实或明确标记为建议值。

## 类似产品可借鉴点

- Linear Triage 使用统一收件箱承接待处理项目，但在详情中提供不同的处理动作，并将 snooze 作为暂时隐藏/稍后回来的动作，而不是业务解决状态。
- Sentry 将 unresolved、resolved、ignored 与重新出现条件分开，说明“当前是否需要关注”和“问题是否已解决”应是两个维度。
