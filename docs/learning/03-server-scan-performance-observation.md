# Server 扫描性能观测

## 2026-09-18：PP0064 显式材料预览

安装版诊断复现耗时 171.54 秒：五金来源检查 11.04 秒、内存预览准备 0.17 秒、Server 解析校验 156.24 秒、组装预览 4.06 秒。报表解析计时合计仅 1.65 秒；两次后台采样约 99% 停在 `stat`（文件属性查询）。目录有 4,114 个文件，只有 25 个 Excel。关联订单识别原先先对所有路径执行 `is_file()`，再匹配订单号，且同步和校验重复执行。

改法保留完整子目录及共享订单识别：先匹配文件名中的订单号，只对候选路径查属性；`ReportReadContext` 在一次预览内共享目录名称清单和关联订单结果，下次请求重新发现。报表内容仍按修改时间和大小校验，读取前后变化仍报错，不把一次请求的复用变成跨请求持久缓存。

日志 `report_read_metrics.discovery` 记录目录枚举和关联订单识别（后者可能包含首次枚举，不能直接相加）；`report_metadata_seconds` 记录报表读取装饰器的属性查询时间。`operation_timing.server_parse_phases` 保留内部索引阶段耗时，属于外层 `server_parse` 的细分，不能再与外层相加。界面完成消息使用本次预览计时，预览完成仍必须人工确认才能写入材料。

回归入口：`tests/test_preview_discovery.py`、`tests/test_order_index.py`、`tests/test_macos_ui.swift`。实际提速须以重新安装后的同一入口测量为准；局部目录实验不等于整次预览耗时。

新源码在正式 SQLite 的隔离副本上读取同一 Server 目录，预览总计 17.55 秒，解析校验 7.35 秒。目录枚举一次 8.03 秒，复用 5 次；关联订单候选属性查询 30 次（包括需要排除的目录），识别共 0.32 秒。结果为 PP0064 校验正常、两项五金 SKU 待处理。此测量未确认业务写入，也不是安装版 UI 验收；SMB 状态和系统缓存可能影响跨次耗时比较。

## 本次做法

Server 轻量扫描先枚举根目录下的一级订单文件夹，再按已知 AICNC 目录结构检查 `Optimize file.xml` 和 `nesting_result.xml` 的元数据和标记。标准订单不再递归枚举订单目录中的 PNG、NC、CSV 和其他文件；临时/混单文件夹也只比较报表元数据，完整报表读取留给后续显式处理。订单文件夹本身只用于发现、归属、分组以及新增/删除判断；文件夹 mtime 单独变化不再视为业务变化。修改时间标记使用毫秒精度，避免把纳秒值写入 SQLite REAL 列时发生浮点精度丢失。扫描结果额外记录：

- 扫描耗时（秒，保留两位小数）
- 扫描到的订单文件夹数量
- 登记的相关报表文件数量
- 快速登记的相关报表文件数量
- 复用的订单文件夹数量
- 深度扫描的订单文件夹数量
- 新增、修改、删除数量

这些数据通过 scan-server 返回的 server.scan_stats 提供，同时转换成中文 operation_trace[server]，在订单中心 Server 消息的悬停详情中显示。索引读取详情按文件夹汇总下属 material、板材清单和五金清单数量，只展示少量文件夹示例；完整绝对路径仍保留在索引和具体错误记录中，便于人工定位。

当前标准订单扫描只读取固定候选路径，并通过有限层级的子目录枚举支持一个订单下的多组优化任务；“复用文件夹”和“深度扫描文件夹”仍沿用原有统计口径。“快速检查文件”表示只读取相关 XML 的路径、修改时间和大小，不打开 XML 内容。临时/混单文件夹仍可能递归枚举报表元数据，这是处理边界不同，不属于标准订单 XML 标记扫描，也不表示扫描阶段解析 Excel。

## 索引更新的增量策略

`scan-server` 仍然只做目录、路径以及相关报表文件修改时间和大小的轻量比较，不打开 Excel。随后启动的 `sync-index` 或用户选择文件夹后的完整处理才按需读取和校验材料：

- 未变化的板材清单和 Fittingslist 复用 SQLite 中上次解析出的工厂单身份、订单归属和五金状态；
- 新增、修改或删除报表只重新校验受影响的订单；
- 新生成的 `Optimize file.xml` / `nesting_result.xml` 只做轻量文件存在性检查，不因此重新打开全部 Excel；
- 首次建立索引、显式选定 Server 文件夹或传入 `--full-refresh` 时仍可完整校验。

因此，扫描到 0 个文件变化时，不再重复打开当前 Server 下全部业务 Excel。当前实机 App 记录的 64 秒同步中，约 33 秒用于 112 个文件的登记与解析窗口，约 31 秒用于 13 个订单的重复校验；优化后第二次无变化刷新应主要保留 SQLite 和产物元数据检查。

## 为什么先观测，不提前复杂化

目录快照或增量事件跟踪可能减少 Server 网络盘上的枚举次数，但会引入目录 mtime 不代表子文件内容变化、网络盘事件能力不一致、快照失效和恢复等正确性风险。当前优先记录真实扫描耗时和扫描规模，先确认瓶颈是否实际存在，再依据数据决定是否需要更复杂的算法。

本次未改变 Server 扫描仍为只读的边界，也未改变订单归属和优化状态的业务含义；仅把已确认的文件元数据与索引缓存用于安全复用。真实 SMB 挂载上的耗时改善仍需安装版现场复测。
